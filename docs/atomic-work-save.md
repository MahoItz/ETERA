# Атомарное сохранение работы

## Состояние

Миграция `0009_atomic_save_work.sql` применена в подключённом Supabase как
`20261018103206_atomic_save_work`. Клиентские изменения находятся в рабочей копии;
для действующего сайта требуется выпуск новой сборки.

Перед применением сохранена локальная копия данных каталога:
`work/atomic-save-tests/catalog-before-migration.json` (вне git).
После миграции и проверки с откатом данные полностью совпали с копией:
7 работ, 11 фото, 4 варианта, 4 категории, 6 украшений. Файлы Storage при проверке
не изменялись. Копия содержит метаданные и ссылки, а не содержимое изображений.

## Поведение

`save_work(request_id, work_id, expected_revision, payload)` одной транзакцией:

1. Проверяет администратора, идентификатор запроса и сохранённую квитанцию.
2. Блокирует существующую работу и проверяет исходную версию.
3. Сохраняет категорию, карточку, публикацию, фото и варианты.
4. Сохраняет кандидатов на очистку и квитанцию с полным ответом.

Ошибка любого шага откатывает всё, включая версию, категорию и очередь.
Для повторов используется блокировка идентификатора операции; обновления одной
работы синхронизируются блокировкой строки. Одинаковые названия не участвуют
в определении повторов. Варианты сохраняют свои UUID, дополнительные поля и
связанные фотографии; удаляются только отсутствующие в новом списке варианты.

RPC работает как `SECURITY INVOKER` с существующими RLS и проверкой
`private.is_admin()`. Посетители не могут вызвать RPC; обычные пользователи
не могут сохранить карточку или прочитать квитанции. Администратор видит только
свои квитанции. Сервисный ключ клиенту не нужен.

`WorkSaveSession` сохраняет точный запрос до однозначного ответа сервера.
После сетевой ошибки повтор использует тот же идентификатор и содержимое.
Если транзакция уже завершилась, возвращается сохранённый ответ без повторной
записи. При изменении формы после таймаута сначала разрешается предыдущая
операция, затем новые поля сохраняются с подтверждёнными ID и версией.
При подтверждённом откате можно исправить форму и отправить новую операцию.
Загруженные фото повторно не загружаются.

Состояние повторной попытки живёт до закрытия редактора. Восстановление черновика
после закрытия окна или перезагрузки страницы в эту задачу не входит.
Квитанции автоматически не удаляются, в том числе после удаления работы:
старый запрос не должен создать её заново.

## Очистка файлов

Старые ссылки попадают в `work_photo_cleanup` только при успешном коммите.
После подтверждённого сохранения клиент обрабатывает до 16 записей,
находящихся в очереди не менее 24 часов. Проверяются `photos.url`,
`photos.storage_path`, `variants.image_url`, `tree_ornaments.image_url`
и `works.tree_image`, включая черновики и архив.

Удаляются только управляемые файлы `works/<uuid>.webp` своего бакета.
Внешние адреса, локальные изображения и некорректные URL не превращаются
в удаление объекта из своего Storage. При ошибке проверки или удаления
кандидат остаётся в очереди; сохранение карточки уже считается успешным.
Очередь переживает закрытие страницы. Её обработка запускается при следующих
успешных сохранениях; отдельный периодический обработчик не установлен.

Storage не участвует в транзакции PostgreSQL. Проверка ссылок перед удалением
не блокирует новое конкурентное использование URL. Для произвольного повторного
использования старых URL с абсолютной гарантией потребуется отдельный протокол
жизненного цикла файлов. Неиспользуемые предварительные загрузки после отмены
формы автоматически не удаляются — это безопаснее удаления файла при
неизвестном результате RPC.

## Применение и проверки

В новом окружении применить миграции по порядку до `0009`, затем выпустить
клиент. При отсутствии RPC клиент показывает сообщение о необходимости
обновления БД. Уже открытые страницы со старым клиентом нужно обновить.

```sh
npm ci
npm test
npm run build
npm run lint
```

PGlite установлен только как devDependency. Тесты используют отдельную
PostgreSQL в памяти, действительные SQL-миграции, RLS и ошибки вставки фото /
вариантов. Проверяются полный откат и повтор создания/обновления, потерянный
ответ, устаревшая версия, неизменность UUID вариантов, публикация без фото,
права доступа и сохранность изображений при общей ссылке или сбое Storage.
Один экземпляр PGlite выполняет запросы последовательно; тесты не имитируют
реальные параллельные сессии PostgreSQL.

`tests/atomic-save-work.verify.sql` можно запустить от владельца БД в Supabase
SQL Editor. Скрипт использует существующего администратора, проверяет RPC под
ролью `authenticated`, создаёт тестовые строки в транзакции и завершает её
`ROLLBACK`. Он успешно выполнен в подключённой базе.

В браузере: открыть редактор новой работы, загрузить фото и сохранить.
Затем отредактировать существующую работу, заменить фото и варианты, обновить
страницу и проверить результат. Для проверки потерянного ответа в тестовом
окружении оборвать ответ RPC после коммита и повторить сохранение в том же
редакторе: ID и версия должны остаться результатом первой операции.

## Риски и откат

Миграция добавляет две таблицы и функцию, не переписывая данные каталога
и не меняя существующие политики. Она не восстанавливает ранее удалённые фото
и не объединяет работы с одинаковыми названиями.

Для аварийного отката сначала отключить сохранение в интерфейсе, затем при
необходимости удалить только RPC:

```sql
drop function public.save_work(uuid, uuid, integer, jsonb);
```

Сохранённые работы останутся доступны для чтения. Таблицы квитанций и очистки
сохранить для разбора и безопасного восстановления. Откат клиента на прежнее
сохранение возвращает исходную ошибку частичной записи. Откат SQL-функции
не отменяет успешные пользовательские изменения и удалённые файлы Storage.
