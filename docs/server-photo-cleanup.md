## Общий механизм

`work_photo_cleanup` служит очередью и реестром файлов. Триггеры на `photos`,
`variants`, `tree_ornaments` и `works.tree_image` регистрируют изменения ссылок
в той же транзакции, включая каскадное удаление работы и фотографий вариантов.
Очередь учитывает и `photos.storage_path`. Для общих изображений нет отдельных
правил в редакторе работы и редакторе ёлки.

После снятия ссылки файл ждёт минимум 24 часа по времени БД. Обработчик
проверяет все ссылки, включая черновики, архивные и проданные работы.
Внешние хосты и неуправляемые пути не удаляются. URL своего проекта
нормализуются: учитываются процентное кодирование, параметры и фрагменты.
Управляемые пути — одиночные WebP-файлы в `works/`, длиной до 240 символов.

Протокол удаления:

1. Обработчик блокирует строку реестра и проверяет ссылки.
2. Неиспользуемый файл получает состояние `deleting` и временный идентификатор
   обработки. Триггеры записи ссылок используют ту же блокировку и отклоняют
   ссылки на `deleting` или `deleted` с кодом `55000`.
3. Обработчик повторно проверяет ссылки и своё право обработки непосредственно
   перед Storage API `remove`.
4. Успех фиксируется как `deleted`. Запись реестра остаётся: путь нельзя
   использовать повторно после начала удаления.

Поэтому между проверкой и вызовом Storage API нельзя добавить новую ссылку
через таблицы каталога. Это правило действует и при вызове API старым клиентом.
Административный доступ к БД и сервисным ключам должен соблюдать этот протокол.
Запуск дополнительных программ с прямым удалением в Storage обходит защиту.

Ошибка сохраняется в `last_error`; `attempts` считает попытки, а `available_at`
задаёт следующий запуск с увеличивающейся задержкой. Состояние `deleting`
сохраняется при сбое, чтобы отложенный запрос старого обработчика не удалил
заново используемый файл. Через пять минут незавершённую обработку может
повторить другой экземпляр. Устаревший идентификатор не может подтвердить
новую попытку. Если ответ Storage потерян после удаления, повторное удаление
отсутствующего объекта безопасно завершается и закрывает запись реестра.

## Временные загрузки

Новый клиент вызывает `begin_work_photo_upload` до отправки байтов. Регистрация
создаёт путь UUID и защиту на 24 часа. Ошибка регистрации прерывает загрузку.
Ошибка отправки, сохранения или закрытие редактора оставляет запись для уборки;
обработка не зависит от `useEffect` при закрытии страницы.

При повторном сохранении `renew_work_photo_upload` продлевает защиту. Продлевать
её может только администратор, зарегистрировавший загрузку. Если срок уже истёк
и очистка началась, клиент повторно загружает сохранённый Blob под новым UUID.
В памяти редактора остаются исходные байты, пока фотография не удалена из формы.
После потери ответа сохранения прежний идентификатор операции продолжает
использоваться согласно `WorkSaveSession`; немедленного удаления файла нет.

Для старых клиентов сохраняется загрузка новых неизменяемых путей. Обработчик
также обнаруживает незарегистрированные файлы через чтение метаданных Storage
и защищает их на семь дней с момента обнаружения. При первом включении все
35 существующих файлов получили такой карантин до 25 октября 2026 года.
Используемые файлы после карантина остаются доступны благодаря проверке ссылок.

## Доступ и запуск

Физическое удаление из `work-photos` запрещено роли `authenticated`, включая
администратора в браузере. Перезапись и перемещение существующих объектов
клиентом также не разрешены. Публичное чтение изображений сохранено.

Функция использует встроенный `SUPABASE_SERVICE_ROLE_KEY` только на сервере.
Проверка JWT платформой для неё отключена: вместо пользовательского JWT
обработчик проверяет случайный секрет задания через RPC, доступные только
`service_role`. Пустой или неверный секрет получает `401` до доступа к Storage.
Секрет создаётся в БД, хранится в закрытой `private.photo_cleanup_config` и
не встраивается в исходники, команду cron или клиентскую сборку.

Привилегированные реализации загрузок находятся в `private`. Публичные RPC
работают как `SECURITY INVOKER`; внутренние функции проверяют администратора
и владельца загрузки. После применения миграций новых замечаний Security
Advisor не осталось по сравнению с исходным состоянием.

В новом окружении:

1. Применить миграции по порядку до `0012`. Миграция расписания требует
   платформенные расширения `pg_cron` и `pg_net`.
2. Развернуть `supabase/functions/cleanup-work-photos`, включив `deno.json`,
   `deno.lock`, `index.ts` и `worker.ts`, с `verify_jwt = false`.
3. От владельца БД настроить адрес проекта и публичный API-ключ:

```sql
select private.configure_photo_cleanup('https://PROJECT.supabase.co', 'PUBLISHABLE_KEY');
update private.photo_cleanup_config set enabled = true where id;
select private.dispatch_photo_cleanup();
```

4. Проверить HTTP-ответ запуска в `net._http_response`, затем выпустить клиент
   и обновить ранее открытые страницы. Не выдавать клиенту сервисный ключ.

## Проверки и наблюдение

```sh
npm test
npm run build
npm run lint
deno check --config supabase/functions/cleanup-work-photos/deno.json supabase/functions/cleanup-work-photos/index.ts
```

59 тестов прошли. PGlite проверяет настоящие миграции, права, триггеры,
каскадное удаление, общие ссылки, продление защиты и повторные попытки.
Тесты обработчика проверяют порядок RPC → повторная проверка → Storage →
подтверждение, включая ошибки и потерю ответа. PGlite выполняет запросы
последовательно; реальные параллельные сессии эти тесты не воспроизводят.

`tests/server-photo-cleanup.verify.sql` выполнен в подключённом Supabase
с `ROLLBACK`. Отдельно проверен полный путь cron → Edge Function → Storage API →
подтверждение для заведомо отсутствующего тестового объекта: HTTP `200`,
одна обработанная запись, ошибок нет. Реальные файлы при этом не удалялись;
тестовая строка реестра удалена. Попытка проверки перекрывающихся сессий через
SQL-инструмент не состоялась: инструмент выполнил запросы последовательно.

Просмотр ошибок в SQL Editor владельца БД:

```sql
select storage_path, state, attempts, available_at, last_error
from public.work_photo_cleanup
where last_error is not null
order by available_at;

select id, status_code, content, error_msg
from net._http_response
order by id desc limit 10;
```

Успешное выполнение cron подтверждает отправку запроса, а не успех самого
удаления. Проверять также HTTP-ответ и `last_error`. Обработчик принимает до
16 кандидатов за запуск; нераспознанные ссылки имеют состояние `ignored`.
Ошибки уборки не превращают завершённое сохранение карточки в ошибку.

## Откат

Сначала отключить новые запуски:

```sql
update private.photo_cleanup_config set enabled = false where id;
select cron.alter_job(jobid, active := false)
from cron.job where jobname = 'cleanup-work-photos';
```

Дождаться завершения уже работающих экземпляров Edge Function. Запрос,
успевший пройти последнюю проверку, ещё может завершить удаление. Реестр,
триггеры, ограничения Storage и состояния `deleting` / `deleted` сохранить:
их удаление может разрешить ссылку на уже удалённый файл. Каталог, сохранение
и загрузки продолжат работать, очередь будет накапливаться до восстановления
обработчика. Возврат прежнего клиентского удаления файлов не нужен.

Откат не восстанавливает физически удалённые изображения. Для такого
восстановления требуется отдельная копия байтов; локальная копия метаданных
не заменяет резервную копию Storage.
